# ADR 0001: Гибридная модель статистики (events + агрегаты)

## Контекст
SaaS для изучения слов. Рост от 100 до 100 000+ пользователей.
Полный event log на каждое действие раздул бы таблицу `events`
до сотен миллионов строк.

## Решение
- В `events` — только значимые события жизненного цикла
  (auth, CRUD, смена статуса/коробки, старт/конец сессии).
- Операционные события обучения (viewed/flipped/swiped/reverted)
  в `events` НЕ пишутся — идут в `card_session_history` и агрегаты.
- Агрегаты (`card_stats`, `bucket_stats`, `user_daily_stats`)
  обновляются в одной транзакции с действием.

## Обоснование
- `events` растёт медленно (тысячи строк в день, не миллионы).
- Отчёты строятся на агрегатах — быстро.
- Полная история обучений — в `card_session_history` (партиционирована).

## Последствия
- Нельзя восстановить «что было» из агрегатов — только из `card_session_history`.
- При росте > 10k пользователей — вынос `events` в отдельную БД/ClickHouse.
