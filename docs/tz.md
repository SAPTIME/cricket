# Пайплайн разработки «Сверчка» силами ИИ

## Часть 1. Философия: как разделить работу между ИИ

Три ИИ — это не «три одинаковых помощника», а **три разные роли в команде**. Если использовать их хаотично, они будут дублировать друг друга и противоречить. Нужна чёткая специализация.

| ИИ | Роль в команде | Сильные стороны | Слабые стороны |
|---|---|---|---|
| **DeepSeek** | **Архитектор + Senior-разработчик** | Глубокие рассуждения, длинные ответы, сложная логика, SQL, алгоритмы, проектирование схем, рефакторинг | Нет IDE-контекста, нужно копировать код вручную |
| **GitHub Copilot** | **Пилот в IDE** | Автодополнение в редакторе, работа с текущим файлом, мелкие правки, boilerplate, тесты, docstrings | Не видит проект целиком, слаб в архитектуре |
| **Gemini** | **Tech Lead + Ревьюер + Аналитик** | Огромный контекст (весь репозиторий), мультимодальность (скриншоты UI), документация, ревью, поиск противоречий | Иногда многословен, требует чётких инструкций |

**Ключевой принцип:** DeepSeek **думает**, Copilot **печатает**, Gemini **проверяет**.

## Часть 2. Артефакты (что где живёт)

Перед стартом заведите структуру, которая станет «общим языком» для всех трёх ИИ:

```
/docs
  /tz                     — финальное ТЗ (этот документ)
  /contracts              — API-контракты, схемы БД, DDL
  /specs                  — ТЗ на каждый спринт и задачу
  /decisions              — ADR (Architecture Decision Records)
  /prompts                — шаблоны промптов для ИИ
/backend
/frontend
/tests
/infra
```

**Правило:** любой ИИ получает на вход **актуальный контекст из `/docs`**, а не «вспоминает» из прошлых чатов. Это спасает от галлюцинаций.

## Часть 3. Глобальный пайплайн проекта

### Этап 0. Подготовка (1–2 дня)

| Шаг | ИИ | Что делает | Результат |
|---|---|---|---|
| 0.1 | **DeepSeek** | Финализирует ТЗ, разбивает на спринты и задачи, оценивает трудозатраты | `/docs/tz.md`, `/docs/sprints.md` |
| 0.2 | **DeepSeek** | Проектирует схему БД: DDL, индексы, партиционирование, миграции | `/docs/contracts/db.sql`, ER-диаграмма |
| 0.3 | **DeepSeek** | Проектирует API-контракты: endpoints, request/response, коды ошибок | `/docs/contracts/api.md`, OpenAPI-схема |
| 0.4 | **Gemini** | Ревьюит схему БД и API: ищет противоречия, узкие места, предлагает улучшения | Правки в `/docs/contracts/` |
| 0.5 | **DeepSeek** | Формирует структуру проекта: дерево папок, зависимости, конфиги | `/docs/specs/project-structure.md` |
| 0.6 | **Gemini** | Генерирует ADR: почему выбраны FastAPI, Postgres, Redis, HTMX, гибридная статистика | `/docs/decisions/*.md` |

**Хронология:** DeepSeek → Gemini (ревью) → DeepSeek (правки) → фиксация.

### Этап 1. Скелет проекта (2–3 дня)

| Шаг | ИИ | Что делает |
|---|---|---|
| 1.1 | **DeepSeek** | Пишет `docker-compose.yml`, `Dockerfile`, `.env.example`, `nginx.conf` |
| 1.2 | **Copilot** | В IDE дорабатывает конфиги под локальные нужды (порты, пути) |
| 1.3 | **DeepSeek** | Пишет `pyproject.toml`/`requirements.txt`, настройку Alembic, базовый `main.py` FastAPI |
| 1.4 | **Copilot** | Автодополняет boilerplate: импорты, роутеры, middleware |
| 1.5 | **Gemini** | Загружает весь репозиторий, проверяет: «всё ли на месте, нет ли противоречий в конфигах» |

### Этап 2. Спринты 1–6 (см. ТЗ)

Каждый спринт проходит по **повторяемому циклу** (см. Часть 4).

## Часть 4. Повторяемый цикл спринта

Каждый спринт (2 недели) проходит **8 фаз**. Это ядро пайплайна.

### Фаза 1. Планирование спринта
- **ИИ:** DeepSeek
- **Вход:** ТЗ, описание спринта из `/docs/sprints.md`
- **Задача:** разбить спринт на задачи по 0.5–2 дня, для каждой описать:
  - входные данные,
  - результат,
  - затрагиваемые файлы,
  - тесты,
  - критерий готовности.
- **Выход:** `/docs/specs/sprint-N.md`

### Фаза 2. Проектирование задач
- **ИИ:** DeepSeek → Gemini (ревью)
- **Вход:** `/docs/specs/sprint-N.md`, контракты БД/API
- **Задача:**
  - DeepSeek: для каждой задачи пишет техническую спеку — сигнатуры функций, Pydantic-схемы, SQLAlchemy-модели, последовательность вызовов.
  - Gemini: проверяет спеку на соответствие общему ТЗ и контрактам.
- **Выход:** `/docs/specs/sprint-N-task-M.md`

### Фаза 3. Написание моделей и миграций
- **ИИ:** DeepSeek → Copilot
- **Вход:** спека задачи
- **Задача:**
  - DeepSeek: пишет SQLAlchemy-модели, Alembic-миграции, партиционирование.
  - Copilot: в IDE автодополняет поля, типы, индексы по образцу уже написанных моделей.
- **Выход:** код в `backend/models/`, `backend/migrations/`

### Фаза 4. Написание бизнес-логики
- **ИИ:** DeepSeek → Copilot
- **Вход:** спека задачи, модели
- **Задача:**
  - DeepSeek: пишет сервисы (чистая логика), репозитории (работа с БД), обработчики событий, формулы агрегатов.
  - Copilot: в IDE дописывает типовые куски — CRUD-обёртки, обработку исключений, логирование.
- **Выход:** код в `backend/services/`, `backend/repositories/`

### Фаза 5. Написание API
- **ИИ:** DeepSeek → Copilot
- **Вход:** API-контракт из `/docs/contracts/api.md`
- **Задача:**
  - DeepSeek: пишет роутеры FastAPI, Pydantic-схемы, зависимости (auth, rate-limit, CSRF).
  - Copilot: дописывает boilerplate — валидации, docstrings, `response_model`.
- **Выход:** код в `backend/api/`

### Фаза 6. Написание фронтенда
- **ИИ:** DeepSeek → Copilot → Gemini
- **Вход:** макеты, спека UI
- **Задача:**
  - DeepSeek: пишет Jinja2-шаблоны, HTMX-разметку, Alpine.js-компоненты, Tailwind-классы.
  - Copilot: в IDE дописывает повторяющиеся блоки (формы, таблицы, карточки).
  - Gemini: получает скриншоты готовых экранов (мультимодальность) и проверяет на: адаптивность, доступность, соответствие ТЗ.
- **Выход:** код в `frontend/templates/`, `frontend/static/`

### Фаза 7. Тестирование
- **ИИ:** DeepSeek → Copilot
- **Вход:** спека задачи, готовый код
- **Задача:**
  - DeepSeek: пишет тест-кейсы — что проверяем, какие edge cases, какие граничные значения.
  - Copilot: в IDE дописывает сами тесты по образцу существующих.
- **Выход:** код в `tests/`

### Фаза 8. Ревью и закрытие спринта
- **ИИ:** Gemini → DeepSeek
- **Вход:** весь репозиторий после спринта
- **Задача:**
  - Gemini: загружает весь код, проверяет:
    - соответствие ТЗ,
    - консистентность нейминга,
    - безопасность (SQL-инъекции, XSS, CSRF),
    - производительность (N+1, отсутствие индексов),
    - дублирование кода.
  - DeepSeek: получает список замечаний от Gemini и предлагает конкретные правки.
- **Выход:** `/docs/reviews/sprint-N.md`, исправления в коде

**Хронология спринта:**
```
DeepSeek (план) → DeepSeek (спека) → Gemini (ревью спеки)
   → DeepSeek (модели) + Copilot (IDE)
   → DeepSeek (логика) + Copilot (IDE)
   → DeepSeek (API) + Copilot (IDE)
   → DeepSeek (UI) + Copilot (IDE) → Gemini (скриншоты)
   → DeepSeek (тесты) + Copilot (IDE)
   → Gemini (ревью кода) → DeepSeek (правки)
```

## Часть 5. Дневной микро-цикл (на одну задачу)

Когда работаете над конкретной задачей (например, «эндпоинт свайпа»):

```
1. Открываете /docs/specs/sprint-N-task-M.md
2. DeepSeek: «Вот спека. Напиши код для сервиса swipe_card. Вот контекст:
   модели Card, Session, схема card_stats.»
3. Копируете код в IDE.
4. Copilot: в редакторе просите дописать тесты / docstring / обработку ошибок.
5. Запускаете тесты.
6. Если упало — DeepSeek: «Вот ошибка, вот код, вот тесты. Что не так?»
7. Если сложный баг — Gemini: загружаете весь модуль + стектрейс.
8. Фиксируете решение в /docs/decisions/ или в комментарии к задаче.
```

**Правило:** DeepSeek пишет **первую версию**, Copilot **шлифует в IDE**, Gemini **ловит то, что пропустили оба**.

## Часть 7. Правила передачи контекста между ИИ

Это **самое важное** в мульти-ИИ пайплайне. Без правил будет каша.

### 7.1. Единый источник истины

- ТЗ, контракты, спеки — **только в файлах**, не в чатах.
- Перед каждым запросом к ИИ вы **прикладываете актуальный файл**, а не пересказываете.

### 7.2. Формат передачи

Перед запросом к DeepSeek:
```
[КОНТЕКСТ]
- ТЗ: <вставить релевантный фрагмент>
- Контракт БД: <вставить DDL таблиц>
- Контракт API: <вставить endpoint>
- Существующий код: <вставить модуль>

[ЗАДАЧА]
Напиши сервис X, который делает Y.

[ОГРАНИЧЕНИЯ]
- Python 3.12, async
- SQLAlchemy 2.0
- Без N+1
- Логировать через logger.info
```

Перед запросом к Gemini для ревью:
```
[ЗАДАЧА]
Проверь модуль на:
1. Соответствие ТЗ (фрагмент ниже).
2. Безопасность.
3. Производительность.
4. Дублирование.

[ТЗ]
<фрагмент>

[КОД]
<весь модуль>
```

### 7.3. Что кому НЕ давать

- **Copilot** — не давать архитектурные вопросы (он не видит проект).
- **DeepSeek** — не давать «посмотри весь репозиторий» (не влезет).
- **Gemini** — не давать «напиши мне с нуля большой модуль» (будет многословно и не в стиле проекта; лучше DeepSeek + Copilot).

## Часть 8. Анти-паттерны

| Анти-паттерн | Почему плохо | Как правильно |
|---|---|---|
| Спрашивать всех трёх один и тот же вопрос | Дублирование, противоречия | У каждого своя роль |
| Просить Copilot «спроектировать БД» | Не видит проект, галлюцинирует | DeepSeek |
| Просить DeepSeek «посмотреть весь репозиторий» | Не влезет в контекст | Gemini |
| Копировать код из чата без ревью | Ошибки, несоответствие стилю | DeepSeek пишет → Gemini ревьюит |
| Держать ТЗ только в чатах | Теряется, ИИ «забывают» | Файлы в `/docs` |
| Просить ИИ «сделать всё сразу» | Каша | Дробить на задачи 0.5–2 дня |
| Не фиксировать решения | Повторные обсуждения | ADR в `/docs/decisions/` |

## Часть 11. Практические рекомендации

1. **Один чат DeepSeek = одна задача.** Не смешивайте. Иначе он теряет контекст.
2. **Gemini — для «посмотреть целиком».** Раз в неделю загружайте весь репозиторий и просите обзор.
3. **Copilot — всегда включён.** Это ваш «второй пилот» в IDE, он не мешает.
4. **Версионируйте промпты.** Сохраняйте удачные в `/docs/prompts/`.
5. **Фиксируйте каждое архитектурное решение.** Через 2 недели вы забудете, почему выбрали `citext` вместо `text`. ADR спасёт.
6. **Раз в спринт — «сверка с ТЗ».** Gemini загружает репозиторий и сравнивает с ТЗ. Это ловит дрейф.
7. **Не бойтесь переписывать.** Если DeepSeek выдал плохой код — не мучайте Copilot, попросите DeepSeek переписать с нуля с учётом замечаний Gemini.
8. **Тесты — до кода, где возможно.** DeepSeek пишет тест-кейсы, потом код. Это ловит недопонимание ТЗ на раннем этапе.
9. **Логи и метрики — сразу.** Не «потом добавим». DeepSeek + Copilot делают это дёшево.
10. **Ревью безопасности — отдельным этапом.** Gemini раз в спринт. Это не паранойя, это стандарт.

## Часть 12. Что делать, если ИИ противоречат

Ситуация: DeepSeek предложил одно, Gemini раскритиковал.

**Алгоритм:**
1. Зафиксируйте оба мнения в `/docs/decisions/` как ADR-черновик.
2. Задайте DeepSeek вопрос: «Gemini говорит X. Вот его аргументы. Что ты думаешь?»
3. Если DeepSeek согласен — правьте код.
4. Если не согласен — задайте Gemini: «DeepSeek возражает: Y. Вот его аргументы. Кто прав?»
5. Если оба упёрлись — **решение принимаете вы**, как владелец продукта. Записываете в ADR с обоснованием.

**Важно:** ИИ не должны «договариваться» между собой напрямую — вы медиатор.

Этот пайплайн — **рабочий каркас**. По мере практики вы поймёте, где DeepSeek сильнее, а где Gemini, и скорректируете пропорции. Главное — **не смешивать роли** и **держать истину в файлах, а не в чатах**.

Если нужно, могу:
- Расписать **день 1, день 2, день 3** первого спринта пошагово — с конкретными промптами.
- Сделать **готовые промпты** для каждого типа задач (auth, БД, API, UI, тесты, ревью) — в виде копипасты.
- Составить **чек-лист «готов ли спринт к закрытию»** для Gemini.
